M3 native Rust core#

Result#

The Rust core (crates/cp_anywhere_core) implements the complete declared scope from spec/compatibility.md: MeasureImageIntensity, MeasureObjectIntensity over Cells/Nuclei × DNA/Actin, and MeasureObjectNeighbors same-set Adjacent with directed relationship rows. crates/cp_anywhere_python is a thin PyO3/NumPy binding with no scientific logic of its own; src/cp_anywhere/api.py validates inputs and exposes cp_anywhere.measure(...).

scripts/parity/compare_native.py compares the Rust result against all 13 saved golden fixtures and all 119 declared columns plus the directed relationship table: 1,560 of 1,560 rows pass (1,535 exact, 25 within the spec/features.yaml float64 tolerance). The 25 tolerance rows are all MeasureImageIntensity scalar reductions with errors between 1e-17 and 1e-14 — float64 summation-order variance, not a scope or semantics bug. Full counts and reasons are recorded in spec/native-coverage.yaml and benchmarks/reports/native-parity.json.

cargo test --manifest-path crates/cp_anywhere_core/Cargo.toml
env -u CONDA_PREFIX uv run maturin develop --release --uv
uv run --frozen python scripts/parity/compare_native.py
CP_ANYWHERE_REFERENCE_PYTHON=/path/to/reference/venv/bin/python \
  PYTHONPATH=/path/to/pinned/CellProfiler \
  uv run --frozen pytest

env -u CONDA_PREFIX is required on hosts where both CONDA_PREFIX and VIRTUAL_ENV are set; maturin refuses to build with both present.

Hard-case source decisions#

These follow spec/reference-semantics.md, which records the exact original behavior read from the pinned CellProfiler 4.2.8 and NumPy 1.23.5 sources, not a cleaned-up reimplementation:

  • Integer images are promoted to f64 without dtype-maximum rescaling, matching the reference runner’s Image(..., convert=False).

  • Object-quantile and MAD formulas use n * fraction (not (n-1) * fraction) and n / dimensions, matching the original module exactly.

  • Maximum-intensity coordinate ties are resolved by a literal Rust port of NumPy 1.23.5’s introsort (numpy_argsort/argsort_range/ numpy_heapsort in lib.rs), derived from numpy/core/src/npysort/quicksort.cpp and npysort_heapsort.h at de82cd9468704a033702974010ee7e7efc85b393 (BSD-3-Clause; see licenses/numpy.txt and THIRD_PARTY_NOTICES.md). A stable per-object sort does not reproduce the golden tie-break positions; this port does.

  • Same-set adjacent neighbors use only the first two center axes even in 3D (z/y, omitting x) for nearest-distance and angle, a separate ordering for distance/angle selection versus the ID ordering, and the original centrosome.outline.outline-equivalent first-two-axes diagonal outline (also applied unchanged in 3D). These are preserved reference quirks, not defects introduced by this port.

  • Sparse object IDs keep their array position through the maximum label; missing slots are not compacted.

Resource and memory contract#

  • Inputs: 2D or 3D only, nonzero shape, checked shape-product multiplication (checked_mul), matching channel/object/mask lengths, labels must be unsigned and <= MAX_LABEL (1,000,000; a documented limit, not an attempt to allocate u32::MAX rows).

  • crates/cp_anywhere_python/src/lib.rs borrows C-contiguous f64 image arrays and u32 label arrays directly as slices — no copy for that common case. src/cp_anywhere/api.py performs exactly one conversion via np.ascontiguousarray for other numeric dtypes or non-contiguous input; it does not claim zero-copy for those cases.

  • The kernel runs with py.detach(...) (PyO3’s GIL release), so Rust work does not hold the GIL. Callers must not mutate input arrays while measure() is running, since the Rust side holds borrowed slices for the call’s duration.

  • Rejected inputs: 1D or higher-than-3D shapes, boolean/float label arrays, non-real-numeric image dtypes, mismatched shapes, labels above MAX_LABEL, and (when neighbors are selected) no Cells object set.

  • The core (cp_anywhere_core) has no Python, filesystem, or platform dependency: Input/ResultTable are plain Rust types over borrowed slices, which keeps a future WASM target possible without a rewrite.

API#

cp_anywhere.measure(images, objects, *, mask=None, image_id="Image", families=None) returns a frozen MeasurementResult with .features (mirroring the golden JSON structure: Image scope holds scalars, object scopes hold NumPy arrays aligned to .object_ids), .object_ids, and .relationships (directed edges with both image/object IDs). .rows() gives a long table; .to_csv()/.to_json() write it and the reference-shaped structure respectively, with nonfinite floats encoded explicitly ({"nonfinite": "NaN"}, "+Infinity", "-Infinity") rather than silently dropped or turned into null. families restricts computation to a subset of ("image_intensity", "object_intensity", "neighbors") so later benchmarking can time an equivalent subset without computing unselected families.

The CLI (cp-anywhere --image NAME=PATH --objects NAME=PATH [--mask PATH] --output PATH) loads saved NPY arrays and writes CSV or JSON depending on the output suffix.

Wheel build and installed-wheel smoke test#

maturin build --release produced cp_anywhere-0.1.0-cp311-abi3-macosx_11_0_arm64.whl. It was installed into a fresh, isolated uv venv with no project checkout on sys.path. The imported module resolved to that venv’s site-packages (not the source tree), and cp_anywhere.measure(...) on the touching_gradient fixture returned all 119 declared columns. This proves the installed wheel, not just the editable development install, produces the full declared scope.

cargo fmt --check and cargo clippy --all-targets are clean for both crates. cargo test passes the one Rust unit test (invalid shape and over-limit label rejection). The full project pytest suite (22 tests, including the real CellProfiler 4.2.8 replay) passes.

Known limitations#

  • Only the one rejects_bad_shape_and_large_id Rust unit test exists; most correctness assurance currently comes from the Python-side golden parity script, not from Rust-level property tests (e.g. proptest) on the sorting or neighbor kernels.

  • Timing against cp_measure and against a WASM build is explicitly out of scope for M3; see docs/decisions/0002-rust-core.md and M4/M6.

M4 WASM feasibility and browser integration spike#

Result#

The Rust core compiles unmodified to wasm32-unknown-unknown (no feature gates needed; cp_anywhere_core has no dependencies beyond std). crates/cp_anywhere_wasm is a thin wasm-bindgen binding (JSON in/out for small metadata, typed arrays for the numeric payload) built with wasm-pack build crates/cp_anywhere_wasm --target web --release, producing a cp-anywhere-wasm npm package consumed by a real Vite example (examples/browser-vite) that runs the module inside a dedicated web worker.

Both declared families run entirely client-side with verified parity, across the full declared manifest (2D and 3D). A real, reproducible headless-Chromium run (Playwright, not a mock DOM; examples/browser-vite/run-browser-check.mjs) executed the worker against all 13 declared golden fixtures and scripts/parity/compare_wasm.py compared every result against the same original CellProfiler 4.2.8 golden fixtures used by the native build:

  • 1,560 of 1,560 rows pass (1,533 exact, 27 within the declared float64 tolerance; zero failures). 13 fixtures × 120 rows (119 features + 1 relationship table) — the identical row count the native build passes (docs/native.md), closing M5’s “100% … in native Rust, Python, and WASM” gate for the current declared manifest.

  • The 27 tolerance rows are the same MeasureImageIntensity reduction-order families already seen in the native build (docs/native.md), plus two Neighbors_AngleBetweenNeighbors_Adjacent rows at 1e-14-scale absolute / 1e-16-scale relative error — consistent with a transcendental-function (acos/atan2) last-bit difference between wasm32’s and native arm64’s libm, not a computation bug.

Browser demo and npm package#

examples/browser-vite is a real Vite project (not a static mockup): its src/worker.ts imports the generated cp-anywhere-wasm package, fetches each fixture’s raw binary arrays (see below), calls measure(), and posts the result back; src/main.ts drives the worker from the page and renders status in #status. npm run build produces a genuine production bundle:

dist/index.html                             0.46 kB
dist/assets/worker-*.js                     ~6.3 kB
dist/assets/cp_anywhere_bg-*.wasm         205.89 kB  (91.27 kB gzip-equivalent)
dist/assets/index-*.js                      ~2.0 kB

npm run preview (or run-browser-check.mjs’s own tiny static server) serves this real build; nothing is dev-server-only or dynamically recompiled per request.

Typed-array inputs, output conversion, memory#

  • Input: measure(shape, image_names, images, object_names, objects, mask, image_id, families) takes real typed arrays (Uint32Array/Float64Array/Uint8Array) across the wasm-bindgen boundary — the plan’s “typed-array inputs” requirement. wasm-bindgen copies &[T] parameters into wasm linear memory once per call; this is the standard, documented cost of that FFI pattern (see crates/cp_anywhere_wasm/src/lib.rs), not something hidden.

  • Numeric fixture data is fetched as raw binary, not JSON. The first export attempt used plain JSON and failed immediately: nonfinite’s pixel array contains literal NaN/Infinity, which are not valid JSON numbers (JSON.parse correctly rejects them). scripts/wasm/export_fixtures.py now writes small JSON metadata (shape, names, image_id) plus .images.f64 / .objects.u32 / .mask.u8 raw binary blobs; the worker fetches each as an ArrayBuffer and constructs a typed-array view directly over the bytes, which preserves the exact IEEE754 bit pattern and is also the more realistic typed-array transfer path for a browser demo.

  • Output conversion: measure() returns one JSON string matching MeasurementResult.to_json()’s shape exactly (same {"nonfinite": "NaN"}-style markers), so the same Python comparator (scripts/parity/compare_cp_measure.py’s compare_feature/ compare_relationships) verifies both the native and the WASM result without a second, independently-trusted comparison implementation.

  • Memory: WebAssembly.Memory.buffer.byteLength was 3,538,944 bytes (~3.46 MiB) after running all 13 fixtures sequentially in one worker instance — a post-hoc read, not a tracked peak (see Known limitations).

Worker execution and browser compatibility#

The module runs inside a dedicated Worker({ type: "module" }), loaded via Vite’s new URL(...) + new Worker(...) pattern, which Vite bundles correctly (confirmed by the production build above). Testing used real headless Chromium (Playwright, Chrome for Testing 159.0.8154.6); Firefox and Safari were not tested in this spike (see Known limitations). crossOriginIsolated / COOP-COEP were not required for this single-threaded wasm-bindgen build.

Browser integration: Zarr, ONNX Runtime Web, DuckDB-WASM#

What this is#

examples/zarr-onnx-duckdb/ is a real, end-to-end browser integration proving the pieces named in the plan work together with cp-anywhere’s own WASM build, with no mocked stage:

  1. zarrita.js reads a real OME-Zarr v2 array (public/dna.zarr, written by scripts/zarr/export_demo_fixture.py) over HTTP.

  2. onnxruntime-web runs a real, checked ONNX graph (public/threshold.onnx) against that array, producing an integer label mask.

  3. cp-anywhere-wasm (this project’s own Rust/WASM kernel, the same build verified in docs/wasm.md) measures the Zarr image using that ONNX-produced mask as the Cells object labels.

  4. DuckDB-WASM loads cp-anywhere’s own measurement output into a SQL table and exports it as a real Parquet file (COPY ... FORMAT PARQUET).

scripts/zarr/validate_export.py then validates that Parquet file with native DuckDB (not the WASM build under test) and cross-checks every value against a fresh, from-source native Python cp_anywhere.measure() call on the identical Zarr bytes and mask – proving the browser pipeline produced numerically correct output, not just that it ran without an error.

Why the mask, not a trained segmentation model#

The plan names “ONNX Runtime Web label masks” as an integration target, not a trained segmentation model (cp-anywhere does not ship or depend on one). scripts/zarr/export_demo_fixture.py builds a tiny, real ONNX graph – Greater(image, 0.5) -> Cast(..., INT32) – checked with onnx.checker.check_model and independently evaluated with onnx.reference.ReferenceEvaluator before the browser ever sees it. This is a deterministic threshold, not instance segmentation: disconnected foreground pixels all share label 1. It exists to exercise the real Zarr -> ONNX -> cp-anywhere -> DuckDB pipeline end to end, not to claim CellProfiler-parity object identification from a thresholding operator (see “Known limitations” below).

Known limitations#

  • Not scientific segmentation. The ONNX model is a fixed-threshold demo graph (see above), not a learned model or connected-component instance segmentation. Scientific parity for this demo’s mask is not claimed or meaningful; cp-anywhere’s own measurement parity is established separately and exhaustively in docs/native.md and docs/wasm.md against real CellProfiler 4.2.8 fixtures.

  • Network required at run time. DuckDB-WASM fetches its parquet extension from extensions.duckdb.org on the first LOAD parquet; this demo does not vendor that extension. For a fully offline/CSP-restricted deployment, fetch and serve https://extensions.duckdb.org/v1.5.4/wasm_mvp/parquet.duckdb_extension.wasm locally and set custom_extension_repository before LOAD parquet (verify the embedded engine version first – it does not always match the npm package version; see the exact version-pinning caveats this was derived from in ~/.hermes/cache/scratch/cp-anywhere-browser-integration-research.md if still present, or re-derive from DuckDB-WASM’s own docs).

  • Single browser tested. Only Chromium (via Playwright) was exercised. No SharedArrayBuffer/COOP/COEP cross-origin isolation was used or is required for this single-threaded WASM MVP path.

  • 2D only. The Zarr/ONNX stage of this demo uses one 2D channel; this does not affect cp-anywhere’s own 2D/3D coverage (docs/native.md, docs/wasm.md), which is unrelated and already complete.

  • Not an OME-Zarr multiscale/metadata demo. The written Zarr array has an empty .zattrs (no OME-NGFF multiscale metadata, no multichannel axes); it is a plain single-chunk array read for its pixel data only.

M6 performance report#

Headline result#

Fixed a real O(pixels^2) bug in the neighbors kernel, found by profiling a per-workload throughput regression the plan explicitly warns against hiding behind an aggregate: before the fix, cp-anywhere was 3.6x slower than the pinned cp_measure baseline on the grid_large workload (256 objects, 192x192 px), even though every smaller workload was already much faster. After the fix, all four representative workloads beat the baseline individually, and WASM round-trip times fell by 11x-33x at the same time.

How the bug was found#

crates/cp_anywhere_core/src/lib.rs’s “touching” check (used for PercentTouching in MeasureObjectNeighbors) needs to know, for every outline pixel of object k, whether any pixel within a small fixed radius (1.5 px) belongs to a different object. The original implementation tested that by scanning every pixel in the whole image for each outline pixel – an accidental O(perimeter_pixels * total_pixels) algorithm when O(perimeter_pixels) suffices, because the actual predicate only ever depends on a handful of neighboring offsets.

This was invisible in the declared fixture set’s smallest three workloads (it is a constant-factor cost there) but dominates at grid_large scale (36,864 px, 256 objects): a cargo bench run that split the combined object_intensity_and_neighbors timing by family (crates/cp_anywhere_core/benches/throughput.rs’s by_family group) showed neighbors alone was 151.45 ms on grid_large vs 9.68 ms on grid_medium – roughly a 15.6x time increase for a 4x object-count / 4x pixel-count increase, consistent with an O(pixels * objects) or O(pixels^2) pattern, not the near-linear scaling object_intensity showed over the same step (0.44 ms -> 2.18 ms, ~5x).

The fix#

Replaced the whole-image scan with a bounded local-neighborhood check using the same shifted(index, shape, delta) helper the adjacent-relationship loop just below it already used correctly: a small, fixed Cartesian product of candidate offsets (9 for 2D, 8 for 3D) covering exactly the same set of relative positions the original predicate tested, reusing the project’s existing bounds-checked index arithmetic instead of adding a new primitive. The predicate itself was not touched – including its asymmetric, reference-preserving 3D offset range (d == 0 || d == -1, not a symmetric radius) – only how it is evaluated changed, from O(total pixels) to O(1) per outline pixel.

Correctness was re-verified immediately after the change, not assumed:

cargo test --manifest-path crates/cp_anywhere_core/Cargo.toml   # pass
uv run --frozen python scripts/parity/compare_native.py          # 1440/1440 pass (unchanged)
# rebuild WASM, re-export fixtures, rebuild demo, re-run in Chromium:
uv run --frozen python scripts/parity/compare_wasm.py            # 1440/1440 pass (unchanged)

Both parity counts are bit-for-bit identical to before the fix – the change is a pure performance fix, not a semantics change.

CI regression gate#

scripts/benchmarks/check_regression.py compares a fresh benchmarks/reports/native-rust-baseline.json against the committed benchmarks/baseline/native-rust-committed.json, failing only when a workload is more than 20% slower than committed – never on an improvement, and never on noise within that margin, per the plan’s explicit warning against hard-failing on noisy single-run CI timing. .github/workflows/benchmark.yml runs the full benchmark -> report -> throughput-gate -> regression-check chain on a weekly schedule and on manual dispatch (not on every PR, for the same noise reason), uploading the raw report as a 90-day build artifact for trend-watching.

To intentionally accept a new baseline after a verified, deliberate change, regenerate benchmarks/reports/native-rust-baseline.json and copy it over benchmarks/baseline/native-rust-committed.json.

Known limitations#

  • Single machine, single run per report regeneration (Criterion’s own statistical sampling, 100 samples per workload, is the only within-run repetition; see benchmark-analysis’s guidance on single-rep measurements – the gaps here are large (5.8x-29x, 21x on the previously-regressed workload), well above the “order of magnitude” bar for a conclusion to survive run-to-run noise).

  • cp_measure’s own timing snapshot (benchmarks/baseline/initial-cp-measure-timing.json) was captured once, in M2, on this same machine; it was not re-measured in M6. Re-running it would only change the comparison if this machine’s absolute performance characteristics changed between M2 and M6, which they did not (same hardware, same session).

  • The regression-gate tolerance (20%) and the schedule (weekly, not per-PR) are both judgment calls aimed at the plan’s explicit warning against noisy single-run CI failures; they have not been tuned against real CI runner variance data, because this session cannot execute a real scheduled GitHub Actions run.
