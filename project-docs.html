M3 native Rust core#

Result#

The Rust library (crates/cp_anywhere) implements the complete declared scope from spec/compatibility.md: MeasureImageIntensity, MeasureObjectIntensity over Cells/Nuclei × DNA/Actin, and MeasureObjectNeighbors same-set Adjacent with directed relationship rows. crates/cp_anywhere_python is a thin PyO3/NumPy binding with no scientific logic of its own; src/cp_anywhere/api.py validates inputs and exposes cp_anywhere.measure(...).

scripts/parity/compare_native.py compares the Rust result against all 13 saved golden fixtures and all 119 declared columns plus the directed relationship table: 1,560 of 1,560 rows pass (1,535 exact, 25 within the spec/features.yaml float64 tolerance). The 25 tolerance rows are all MeasureImageIntensity scalar reductions with errors between 1e-17 and 1e-14 — float64 summation-order variance, not a scope or semantics bug. Full counts and reasons are recorded in spec/native-coverage.yaml and benchmarks/reports/native-parity.json.

Hard-case source decisions#

These follow spec/reference-semantics.md, which records the exact original behavior read from the pinned CellProfiler 4.2.8 and NumPy 1.23.5 sources, not a cleaned-up reimplementation:

  • Integer images are promoted to f64 without dtype-maximum rescaling, matching the reference runner’s Image(..., convert=False).

  • Object-quantile and MAD formulas use n * fraction (not (n-1) * fraction) and n / dimensions, matching the original module exactly.

  • Maximum-intensity coordinate ties are resolved by a literal Rust port of NumPy 1.23.5’s introsort (numpy_argsort/argsort_range/ numpy_heapsort in lib.rs), derived from numpy/core/src/npysort/quicksort.cpp and npysort_heapsort.h at de82cd9468704a033702974010ee7e7efc85b393 (BSD-3-Clause; see licenses/numpy.txt and THIRD_PARTY_NOTICES.md). A stable per-object sort does not reproduce the golden tie-break positions; this port does.

  • Same-set adjacent neighbors use only the first two center axes even in 3D (z/y, omitting x) for nearest-distance and angle, a separate ordering for distance/angle selection versus the ID ordering, and the original centrosome.outline.outline-equivalent first-two-axes diagonal outline (also applied unchanged in 3D). These are preserved reference quirks, not defects introduced by this port.

  • Sparse object IDs keep their array position through the maximum label; missing slots are not compacted.

Resource and memory contract#

  • Inputs: 2D or 3D only, nonzero shape, checked shape-product multiplication (checked_mul), matching channel/object/mask lengths, labels must be unsigned and <= MAX_LABEL (1,000,000; a documented limit, not an attempt to allocate u32::MAX rows).

  • crates/cp_anywhere_python/src/lib.rs borrows C-contiguous f64 image arrays and u32 label arrays directly as slices — no copy for that common case. src/cp_anywhere/api.py performs exactly one conversion via np.ascontiguousarray for other numeric dtypes or non-contiguous input; it does not claim zero-copy for those cases.

  • The kernel runs with py.detach(...) (PyO3’s GIL release), so Rust work does not hold the GIL. Callers must not mutate input arrays while measure() is running, since the Rust side holds borrowed slices for the call’s duration.

  • Rejected inputs: 1D or higher-than-3D shapes, boolean/float label arrays, non-real-numeric image dtypes, mismatched shapes, labels above MAX_LABEL, and (when neighbors are selected) no Cells object set.

  • The library (cp_anywhere) has no Python, filesystem, or platform dependency: Input/ResultTable are plain Rust types over borrowed slices, which keeps a future WASM target possible without a rewrite.

API#

cp_anywhere.measure(images, objects, *, mask=None, image_id="Image", families=None) returns a frozen MeasurementResult with .features (mirroring the golden JSON structure: Image scope holds scalars, object scopes hold NumPy arrays aligned to .object_ids), .object_ids, and .relationships (directed edges with both image/object IDs). .rows() gives a long table; .to_csv()/.to_json() write it and the reference-shaped structure respectively, with nonfinite floats encoded explicitly ({"nonfinite": "NaN"}, "+Infinity", "-Infinity") rather than silently dropped or turned into null. families restricts computation to a subset of ("image_intensity", "object_intensity", "neighbors") so later benchmarking can time an equivalent subset without computing unselected families.

The CLI (cp-anywhere --image NAME=PATH --objects NAME=PATH [--mask PATH] --output PATH) loads saved NPY arrays and writes CSV or JSON depending on the output suffix.

Known limitations#

  • Only the one rejects_bad_shape_and_large_id Rust unit test exists; most correctness assurance currently comes from the Python-side golden parity script, not from Rust-level property tests (e.g. proptest) on the sorting or neighbor kernels.

  • Timing against cp_measure and against a WASM build is explicitly out of scope for M3; see docs/decisions/0002-rust-core.md and M4/M6.

M4 WASM feasibility and browser integration spike#

Result#

The Rust core compiles to wasm32-unknown-unknown with its default features, including the .cppipe executor. The core does not depend on Python or browser bindings. crates/cp_anywhere_wasm is a thin wasm-bindgen binding (JSON in/out for small metadata, typed arrays for the numeric payload). The build script scripts/wasm/build_package.py uses wasm-pack and names the npm package cp-anywhere. The Vite example (examples/browser-vite) that runs the module inside a dedicated web worker.

Both measurement and segmentation run entirely client-side with verified parity against the real CellProfiler 4.2.8 oracle. A real, reproducible headless-Chromium run (Playwright, not a mock DOM; examples/browser-vite/run-browser-check.mjs) executes the worker against:

  • All 13 declared measurement golden fixtures (2D and 3D) via measure(), compared by scripts/parity/compare_wasm.py – 1,560 of 1,560 rows pass (1,533 exact, 27 within the declared float64 tolerance; zero failures). 13 fixtures × 120 rows (119 features + 1 relationship table) – the identical row count the native build passes (docs/native.md), closing M5’s “100% … in native Rust, Python, and WASM” gate for the current declared manifest.

  • All 100 segmentation golden fixtures (fixtures/segmentation/) via identifyPrimaryObjects(), compared by scripts/parity/compare_wasm_segmentation.py – 100 of 100 pass exactly on labels and object count (one fixture’s scalar threshold uses the same documented, narrow, label-safe float32/float64 tolerance exception as the native/Python build; see tests/segmentation/test_reference_alignment.py’s _KNOWN_THRESHOLD_MAP_TOLERANCE_GAP) – see docs/segmentation-coverage.md.

The 27 measurement tolerance rows are the same MeasureImageIntensity reduction-order families already seen in the native build (docs/native.md), plus two Neighbors_AngleBetweenNeighbors_Adjacent rows at 1e-14-scale absolute / 1e-16-scale relative error – consistent with a transcendental-function (acos/atan2) last-bit difference between wasm32’s and native arm64’s libm, not a computation bug.

Segmentation: identifyPrimaryObjects#

identifyPrimaryObjects(pixels, rows, cols, mask, config_json) shares its exact settings surface with the Python binding (cp_anywhere::segmentation::build_config/ConfigParams – see spec/segmentation-modules.md), so the same config_json field names (threshold_method, unclump_method, watershed_method, …) work identically in both bindings, eliminating a second, driftable mapping. Its result (SegmentationResult) is exposed as typed-array/scalar getters (labels, smallRemovedLabels, objectCount, threshold, thresholdMap, guideThreshold), not a JSON string: the label arrays are the same size as the input image, unlike measure()’s much smaller per-object feature output, so JSON-encoding them would be wasteful. identifyPrimaryObjectsJson(input) is a JSON-string overload (pixels as a plain array) kept for parity with measureJson, for debugging/small inputs without constructing a typed array by hand.

examples/zarr-onnx-duckdb demonstrates this chained into a full Zarr -> segmentation -> measurement -> Parquet pipeline in a real browser (see docs/browser-integration.md) – this is the shape a browser-based consumer needing both segmentation and feature extraction from cp-anywhere would use, not a theoretical API surface.

Typed-array inputs, output conversion, memory#

  • Input: measure(shape, image_names, images, object_names, objects, mask, image_id, families) takes real typed arrays (Uint32Array/Float64Array/Uint8Array) across the wasm-bindgen boundary — the plan’s “typed-array inputs” requirement. wasm-bindgen copies &[T] parameters into wasm linear memory once per call; this is the standard, documented cost of that FFI pattern (see crates/cp_anywhere_wasm/src/lib.rs), not something hidden.

  • Numeric fixture data is fetched as raw binary, not JSON. The first export attempt used plain JSON and failed immediately: nonfinite’s pixel array contains literal NaN/Infinity, which are not valid JSON numbers (JSON.parse correctly rejects them). scripts/wasm/export_fixtures.py now writes small JSON metadata (shape, names, image_id) plus .images.f64 / .objects.u32 / .mask.u8 raw binary blobs; the worker fetches each as an ArrayBuffer and constructs a typed-array view directly over the bytes, which preserves the exact IEEE754 bit pattern and is also the more realistic typed-array transfer path for a browser demo.

  • Output conversion: measure() returns one JSON string matching MeasurementResult.to_json()’s shape exactly (same {"nonfinite": "NaN"}-style markers), so the same Python comparator (scripts/parity/compare_cp_measure.py’s compare_feature/ compare_relationships) verifies both the native and the WASM result without a second, independently-trusted comparison implementation.

  • Memory: WebAssembly.Memory.buffer.byteLength was 3,538,944 bytes (~3.46 MiB) after running all 13 fixtures sequentially in one worker instance — a post-hoc read, not a tracked peak (see Known limitations).

Browser integration: Zarr, ONNX Runtime Web, DuckDB-WASM#

What this is#

examples/zarr-onnx-duckdb/ is a real, end-to-end browser integration proving the pieces named in the plan work together with cp-anywhere’s own WASM build, with no mocked stage:

  1. zarrita.js reads a real OME-Zarr v2 array (public/dna.zarr, written by scripts/zarr/export_demo_fixture.py) over HTTP.

  2. onnxruntime-web runs a real, checked ONNX graph (public/threshold.onnx) against that array, producing a reference threshold mask (logged for comparison; not used downstream – see “Why the mask is only a reference” below).

  3. cp-anywhere’s own identifyPrimaryObjects (the same CellProfiler-compatible, oracle-verified segmentation the Python binding exposes – Otsu threshold + Intensity declumping/watershed in this demo) segments the same Zarr pixels into real object labels.

  4. cp-anywhere’s measure() (this project’s own Rust/WASM kernel, the same build verified in docs/wasm.md) measures the Zarr image using cp-anywhere’s own segmentation output as the Cells object labels – both segmentation and feature extraction now come from cp-anywhere, not just the latter.

  5. DuckDB-WASM loads cp-anywhere’s own measurement output into a SQL table and exports it as a real Parquet file (COPY ... FORMAT PARQUET).

scripts/zarr/validate_export.py then validates that Parquet file with native DuckDB (not the WASM build under test) and cross-checks every value – and the segmentation’s own object_count/threshold – against a fresh, from-source native Python cp_anywhere.identify_primary_objects()

  • cp_anywhere.measure() call on the identical Zarr bytes – proving the browser pipeline (both its segmentation and its measurement) produced numerically correct output, not just that it ran without an error.

Why the mask is only a reference#

The ONNX threshold model (public/threshold.onnx, a checked Greater(image, 0.5) -> Cast(..., INT32) graph) still runs in this demo to exercise the real Zarr -> ONNX -> cp-anywhere -> DuckDB pipeline named in the plan, and its foreground pixel count is logged for comparison. Its output is not fed into measurement: main.ts segments with cp-anywhere’s own identifyPrimaryObjects instead (step 3 above), so the object labels measurement actually uses come from real CellProfiler- compatible segmentation (with declumping), not a disconnected-foreground threshold mask that would merge every touching object into a single label. A future revision could use the ONNX path for a learned model (e.g. StarDist) instead of the fixed-threshold demo graph; that remains independent of cp-anywhere’s own segmentation path either way.

M6 performance report#

Headline result#

Fixed a real O(pixels^2) bug in the neighbors kernel, found by profiling a per-workload throughput regression the plan explicitly warns against hiding behind an aggregate: before the fix, cp-anywhere was 3.6x slower than the pinned cp_measure baseline on the grid_large workload (256 objects, 192x192 px), even though every smaller workload was already much faster. After the fix, all four representative workloads beat the baseline individually, and WASM round-trip times fell by 11x-33x at the same time.

How the bug was found#

crates/cp_anywhere/src/lib.rs’s “touching” check (used for PercentTouching in MeasureObjectNeighbors) needs to know, for every outline pixel of object k, whether any pixel within a small fixed radius (1.5 px) belongs to a different object. The original implementation tested that by scanning every pixel in the whole image for each outline pixel – an accidental O(perimeter_pixels * total_pixels) algorithm when O(perimeter_pixels) suffices, because the actual predicate only ever depends on a handful of neighboring offsets.

This was invisible in the declared fixture set’s smallest three workloads (it is a constant-factor cost there) but dominates at grid_large scale (36,864 px, 256 objects): a cargo bench run that split the combined object_intensity_and_neighbors timing by family (crates/cp_anywhere/benches/throughput.rs’s by_family group) showed neighbors alone was 151.45 ms on grid_large vs 9.68 ms on grid_medium – roughly a 15.6x time increase for a 4x object-count / 4x pixel-count increase, consistent with an O(pixels * objects) or O(pixels^2) pattern, not the near-linear scaling object_intensity showed over the same step (0.44 ms -> 2.18 ms, ~5x).

The fix#

Replaced the whole-image scan with a bounded local-neighborhood check using the same shifted(index, shape, delta) helper the adjacent-relationship loop just below it already used correctly: a small, fixed Cartesian product of candidate offsets (9 for 2D, 8 for 3D) covering exactly the same set of relative positions the original predicate tested, reusing the project’s existing bounds-checked index arithmetic instead of adding a new primitive. The predicate itself was not touched – including its asymmetric, reference-preserving 3D offset range (d == 0 || d == -1, not a symmetric radius) – only how it is evaluated changed, from O(total pixels) to O(1) per outline pixel.

Correctness was re-verified immediately after the change, not assumed:

# rebuild WASM, re-export fixtures, rebuild demo, re-run in Chromium:
uv run --frozen python scripts/parity/compare_wasm.py            # 1440/1440 pass (unchanged)

Both parity counts are bit-for-bit identical to before the fix – the change is a pure performance fix, not a semantics change.

One-time setup (must be done once, outside this repo, before the first release)#

Each registry has different setup steps for a first release of its package:

  1. GitHub “release” environment. Already created (repos/d33bs/cp-anywhere/environments/release), referenced by all three publish workflows’ environment: release. Optional hardening: add required reviewers under Settings -> Environments -> release.

  2. PyPI – zero-touch, even for the first release. PyPI supports a “pending publisher” that creates the project on first use:

    1. Sign in at https://pypi.org/manage/account/publishing/.

    2. Add a pending GitHub publisher: PyPI project name cp-anywhere, owner d33bs, repository cp-anywhere, workflow filename publish-pypi.yml, environment name release.

    3. Nothing else to do – the first tagged release creates the project and publishes to it automatically.

  3. npm – needs one manual publish first. npm’s trusted publishing has no “pending publisher” equivalent: a trusted publisher can only be attached to a package that already exists, so the very first publish cannot go through OIDC.

    1. Use a disposable checkout. Publish a bootstrap prerelease so the GitHub workflow can publish the first stable version. For a first stable release of v0.1.0, use:

    3. Enable direct npm publish for the trusted publisher. Publish the first stable version through GitHub Releases, not by hand.

  4. crates.io – needs a token for the first release. Trusted publishing on crates.io reached general availability in 2025, but like npm, the trusted publisher can only be configured for a crate that already exists – so the first publish needs a classic API token.

    1. Sign in at https://crates.io/settings/tokens, create a token scoped to publish-new (and publish-update for later releases).

    3. Size and shape measurements#

MeasureObjectSizeShape is available for 2D label arrays in native Python and WASM. It uses the pinned CellProfiler 4.2.8 reference, with scikit-image 0.21.0 and centrosome 1.2.3.

from cp_anywhere import measure

result = measure(
    {"DNA": dna_image},
    {"Cells": cell_labels},
    families=["object_size_shape"],
    size_shape_calculate_zernikes=True,
    size_shape_calculate_advanced=False,
)

The family measures each supplied object set, without using image intensity or the image mask. Images are still required by the shared measure API. The original three default families are unchanged: request object_size_shape explicitly to add shape columns.

Columns and settings#

All columns have the AreaShape_ prefix. The module supplies:

  • 25 standard columns: area, perimeter, axes, eccentricity, orientation, center coordinates, bounding boxes, form factor, extent, solidity, compactness, Euler number, radii, convex area, Feret diameters, and equivalent diameter.

  • 30 Zernike columns, orders 0 through 9. Enabled by default, matching CellProfiler’s calculate_zernikes setting.

  • 53 advanced columns: spatial, central and normalized moments, Hu moments, the inertia tensor and its eigenvalues. Disabled by default, matching CellProfiler’s calculate_advanced setting.

The two flags select 25, 55, 78, or 108 total columns. Undefined values remain NaN or infinity, rather than becoming zero. The normal result serialization and export methods retain their existing nonfinite-value rules. An empty object set still has the selected schema with empty arrays.

The .cppipe importer accepts revision 3. Its three settings are the object list, Zernike flag, and advanced flag. Each imported module keeps its own settings and object selection, even when a pipeline measures Nuclei, Cells, and Cytoplasm with different flags.

Limits#

  • 3D size/shape measurements are not implemented. A 3D request raises a clear error rather than returning 2D substitutes.

  • The public measurement API requires consecutive object IDs starting at

    1. The real reference produces inconsistently packed columns for sparse labels. The low-level Rust routines preserve that behavior for numerical comparison, but the integrated API rejects it to prevent corrupt row alignment in exports. Other measurement families keep their existing sparse-label support.

  • Numerical checks target the pinned reference environment. Advanced moment reductions reproduce its NumPy/OpenBLAS ARMv8 order; this is not a claim of bitwise agreement with every BLAS implementation.

Verification#

Real reference fixtures cover rectangles, rings, diagonal shapes, nested objects, multiple objects, border objects, single pixels, and empty images. Tests compare every selected column under all four flag combinations. Separate real pipelines run primary, secondary, and tertiary segmentation before size/shape measurement, with different flags for each compartment.

The browser check runs both measureJson and measureWithOptions in real Playwright Chromium, not a simulated WASM runtime. The original eight-argument measure export remains available for existing callers; measureWithOptions adds diagnostic neighbor layers and shape flags.

Granularity#

MeasureGranularity is available for 2D images, in native Python and WASM. It uses the pinned CellProfiler 4.2.8 reference, with scipy 1.9.3 and scikit-image 0.21.0.

from cp_anywhere import measure_granularity

result = measure_granularity(
    dna_image,
    objects={"Cells": cell_labels},
    subsample_size=0.25,  # CellProfiler's own defaults
    image_sample_size=0.25,
    element_size=10,
    granular_spectrum_length=16,
)
result.image[0]  # GS1, the image-level granularity spectrum
result.objects["Cells"][0]  # GS1, one value per Cells object

measure_granularity is a standalone function, separate from the unified measure() family dispatch: CellProfiler’s own module measures one image at a time, with its own subsampling/structuring-element settings, and its result shape (per-scale spectra, not a flat feature table) does not fit the shared measure() contract.

Algorithm#

For each image: optionally downsample for the main granularity computation (subsample_size) and separately for background removal (image_sample_size), using CellProfiler’s own mix of bilinear (order 1) pixel resampling and cubic B-spline (order 3) mask resampling. Subtract a grayscale-opened background (erosion then dilation with a disk structuring element of element_size radius), then repeatedly erode with a radius-1 disk and reconstruct by dilation, recording the percent change in masked mean brightness at each of granular_spectrum_length scales.

Per-object spectra use the same per-scale reconstructed image, rescaled back to full resolution, averaged over each object’s unmasked pixels at full resolution – not the (possibly subsampled) working image directly.

An object with zero pixels under the mask reports NaN at every scale, matching real CellProfiler: its own baseline mean is already NaN, and NaN never recovers through the per-scale subtraction.

Limits#

  • 2D only. Real CellProfiler’s own module divides by orig_shape[dimension] - 1 while rescaling its working image back to full resolution, and raises ZeroDivisionError, unconditionally, for any image with a 1-row or 1-column dimension – confirmed live against the pinned reference. measure_granularity raises a clear ValueError for that case instead of silently producing 0/NaN; there is no real oracle value to match for it.

  • image must already be at the same precision real CellProfiler would have measured. Image(..., convert=True) rescales integer dtypes by their dtype’s max value (identify_primary_objects reproduces this automatically for segmentation inputs, but measure_granularity does not – intensity measurements expect already-scaled float input, the same contract measure()’s other intensity families use) and always downcasts through float32 even for float64 input. The second effect is usually negligible (~1e-7 relative) but is a real precision difference, not a cp-anywhere rounding bug, when reproducing an exact oracle run numerically.

  • The .cppipe importer accepts revision 4 (7 settings: images, “measure within objects?”, objects, both subsampling factors, element size, spectrum length). Every listed image is measured independently and merged into the same MeasurementResult, matching real CellProfiler’s Granularity_<scale>_<image name> feature-naming convention.

Verification#

Real reference fixtures cover CellProfiler’s own defaults, full resolution (no subsampling), uneven subsample/background factors, partial and fully-empty masks, zero/constant/negative images, and multiple simultaneous object sets – 12 cases total, generated by scripts/reference/generate_granularity.py against a live pinned CellProfiler run. A separate real two-image, two-object-set .cppipe pipeline (scripts/cppipe/generate_granularity_pipeline.py) exercises the full IdentifyPrimaryObjects -> IdentifySecondaryObjects -> IdentifyTertiaryObjects -> MeasureGranularity chain end to end.

The browser check runs measureGranularityJson in real Playwright Chromium, not a simulated WASM runtime.

CellProfiler pipeline (.cppipe) import#

cp_anywhere.load_pipeline(path) reads a real CellProfiler .cppipe file and translates the settings of every module this project implements (IdentifyPrimaryObjects, IdentifySecondaryObjects, IdentifyTertiaryObjects, MeasureImageIntensity, MeasureObjectIntensity, MeasureObjectSizeShape, MeasureGranularity, MeasureObjectIntensityDistribution, MeasureTexture, MeasureColocalization, MeasureObjectNeighbors) into cp_anywhere’s own configuration – an existing pipeline’s settings for those modules carry over 1-for-1, with no manual re-entry.

import cp_anywhere

pipeline = cp_anywhere.load_pipeline("my_pipeline.cppipe")
segmentations, derived_objects, measurement = pipeline.run(
    {"DNA": dna_image, "Actin": actin_image}
)

The second result contains both secondary and tertiary object sets. For example, derived_objects["Cytoplasm"].labels contains the tertiary labels. The return value remains a three-item tuple.

This is a settings importer, not a full pipeline execution engine: file-matching/organization modules (Images, Metadata, NamesAndTypes, Groups, …) are recognized and skipped – pipeline.skipped_modules lists them – not executed; you supply already-loaded image arrays by name, same as cp_anywhere.measure.

Every out-of-scope setting (an older pipeline revision, “basic mode”, a non-"Adjacent" MeasureObjectNeighbors distance method, an unimplemented IdentifySecondaryObjects method, and a handful more) raises cp_anywhere.CppipeError naming the exact setting, rather than silently mis-translating it – see spec/cppipe-compatibility.md for the full settings-mapping table, every explicit gap, and how it is verified (real, oracle-generated .cppipe fixtures in fixtures/cppipe/, checked in tests/cppipe/test_cppipe_import.py against the pinned CellProfiler 4.2.8 oracle’s own segmentation output on the same test image). The CLI also accepts a pipeline directly:

cp-anywhere --pipeline my_pipeline.cppipe --image DNA=dna.tif --output result.json

Database export#

MeasurementResult can be written directly to a real Parquet file, a DuckDB database, or a SQLite database (using STRICT tables), on top of the existing to_csv/to_arrow/to_json:

result.to_parquet("result.parquet")  # same long-form rows as to_arrow
result.to_duckdb("results.duckdb")  # wide Per_Image / Per_Cells / ...
result.to_sqlite("results.sqlite")  # same, as SQLite STRICT tables

to_duckdb/to_sqlite write wide tables named Per_Image/ Per_<ObjectName> – matching real CellProfiler’s own ExportToDatabase naming convention – and default to if_exists="append", so processing many images in a loop and calling one of these once per image builds up a single combined dataset, the way CellProfiler’s own batch runs do. Pass if_exists="replace" to start fresh instead.

to_duckdb needs the optional duckdb dependency (pip install cp-anywhere[duckdb]); to_parquet and to_sqlite need nothing beyond this project’s own core dependencies.

For a dense, fixed-size feature array per object instead of long-form rows (e.g. to load straight into a (n_rows, n_features) numpy array), use to_parquet(..., mode="array"): path becomes a directory, one Per_Image.parquet/Per_<ObjectName>.parquet file is written per scope, and each file’s features column is a single fixed-size array per row. The exact ordered feature names for that array are embedded in the file’s own Parquet schema metadata (no sidecar file to go out of sync) – read them back with cp_anywhere.read_parquet_feature_names(path). The CLI exposes this as --output <directory> --parquet-mode array.

to_parquet(..., mode="wide") writes the same per-scope files as mode="array", but as the traditional tabular shape instead – one real, named column per feature, no array/metadata lookup needed (--output <directory> --parquet-mode wide).

For one combined, CytoTable -style table across every object scope – one row per object, scopes joined on object_id, feature columns prefixed by scope name – use to_parquet(..., mode="joined"). path is either a single .parquet file or a directory, in which case it’s written as a real, max_rows_per_file-paginated Parquet dataset via pyarrow.dataset.write_dataset that can accumulate across many images with if_exists="append" (the default): --output <file-or-directory> --parquet-mode joined --join outer|inner --max-rows-per-file N.

The CLI dispatches on --output’s file extension the same way:

cp-anywhere --image DNA=dna.tif --objects Cells=labels.npy \
  --output results.sqlite --if-exists append

See spec/database-export.md for the exact schema (column names and types), why SQLite specifically needs STRICT tables, and how it’s verified (tests/test_database_export.py).
